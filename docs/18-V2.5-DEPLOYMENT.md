# ProCleaning V2.5 — Connected RFQ + Acknowledgement Email

**Status: integration-ready source, NOT connected to any real account.** The ZIP defaults to `mode: 'demo'`. No live Supabase project, verified Resend domain, Turnstile credentials or admin account have been created or configured on your behalf. The public site retains the Cleaning Service demo while the printing-specific RFQ is a separate route.

## Architecture

- `index.html` → CTA to `request-quote.html?type=general` (Cleaning / general service)
- `request-quote.html` → `request-quote.html` (Print Smart RFQ) or `?type=general` (General Inquiry)
- `src/scripts/rfq-live.js` → HTTPS POST to Edge Function with stable idempotency UUID, no mailto.
- Edge Function `submit-rfq` → validates origin, fields, Turnstile, IP/email quotas → calls `create_public_rfq` SQL RPC in one transaction.
- PostgreSQL (`customers`, `rfqs`, `notification_outbox`) → persists and issues reference, enqueues customer receipt + optional staff alert atomically.
- Resend → SMTP-like transactional email API called server-side; outbox stores accepted/failed status. Database success does NOT depend on email success.
- Edge Function `dispatch-emails` → secure worker (requires `EMAIL_WORKER_SECRET`), supports retry queue.
- `tools/business/live-inbox.html` → read-only live staff inbox; Supabase Auth + RLS. **Old V2.4 Dashboard/Customers/Quote Builder/Orders remain browser-local demonstration.**

## Deployment prerequisites

1. Create or choose a separate Supabase **staging** project. Enable Email + Password sign-in in Supabase Authentication. Use HTTPS on the final site.
2. Create a Resend account, verify the sending domain and obtain a scoped API key.
3. Create a Cloudflare Turnstile widget for your exact site hostname. Collect its **public site key** and **private secret**. Siteverify is mandatory server-side.
4. Replace `privacy.html` with the business's approved privacy notice (name of controller, legal basis, retention, rights, cross-border processing), then assess PDPA and DPA obligations for your use case.
5. Install the current Supabase CLI and login to your project:

```bash
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase db push
```

Run the migration on the linked project. Review SQL before applying. Use a fresh project or check naming collisions first.

6. Copy secret field **names** from `supabase/.env.example` (never commit real values) and set using `supabase secrets set`:

```bash
supabase secrets set \
  RESEND_API_KEY='re_...' \
  MAIL_FROM='Quotes <quotes@verified-domain.com>' \
  ADMIN_NOTIFICATION_EMAIL='team@company.com' \
  TURNSTILE_SECRET_KEY='your-private-secret' \
  TURNSTILE_HOSTNAME='your-domain.com' \
  RFQ_RATE_SALT='long-random-secret' \
  EMAIL_WORKER_SECRET='another-long-random-secret' \
  ALLOWED_ORIGINS='https://your-domain.com'
```

`SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are typically provided to Edge Functions by Supabase. Verify they are available on your deployment; **never put them in the frontend config**. Never expose a private secret or Resend API key on GitHub Pages.

7. Deploy the functions:

```bash
supabase functions deploy submit-rfq
supabase functions deploy dispatch-emails
```

The included `supabase/config.toml` sets `verify_jwt = false` because public intake is unauthenticated and the worker authenticates by custom secret. The public function *requires* `ALLOWED_ORIGINS`, Turnstile, and rate limiting; access without those protections is rejected.

8. In `config/public-config.js` set `mode: 'connected'`, `supabaseUrl`, `publishableKey` (client-safe project publishable key), and `turnstileSiteKey`. Only this file contains PUBLIC configuration. Deploy the static frontend via GitHub Pages/Vercel HTTPS. Make `ALLOWED_ORIGINS` match the exact origin (protocol+host+optional port).

9. Create a Supabase Auth staff user in the Authentication dashboard. Copy the staff Auth UUID and authorize via SQL Editor:

```sql
insert into public.admin_users(user_id) values ('STAFF-AUTH-USER-UUID');
```

Only staff users with matching UUID can read customer/RFQ/outbox tables via RLS. Sign into `tools/business/live-inbox.html` (the page verifies staff membership after login). Password and access tokens are not stored in the static site data files. The in-memory session expires on page refresh, requiring sign-in again.

10. **Schedule notification retries** using a trusted scheduler calling `POST https://YOUR-PROJECT.supabase.co/functions/v1/dispatch-emails` with header `x-worker-secret: EMAIL_WORKER_SECRET` every 1–5 minutes (for example via Supabase Cron + Vault, or an authenticated external scheduler). **Without a scheduler, initial send is attempted on intake, but failed emails are only queued and will not auto-retry.** Do not expose the scheduler secret in a public frontend or GitHub workflow. Monitor retry/failed statuses, provider limits, and logs.

## Connected smoke test

- Test a fake internal test identity and example quote only on staging. Complete Turnstile. Click Submit once.
- Confirm the server returned an RFQ reference and `rfqs` has exactly one record; matching customer and outbox rows exist.
- Refresh, sign in to Live Inbox as authorized staff, confirm RFQ details and outbox statuses.
- Inspect Resend dashboard for receipt and admin notification; `sent` means *accepted by provider*, **not verified delivery to mailbox**. Check inbox/spam and provider delivery status separately.
- Re-POST with the same `submission_id` and payload and verify the same reference (one RFQ). Different payload + same ID must return 409.
- Simulate email API failure: RFQ remains saved; outbox is queued/retry. Worker retry should eventually move it to sent or failed.
- Attempt unauthorized PostgREST access (anon or non-staff token): it must return no RFQ rows. Attempt invalid Turnstile and origin: request rejected.
- Test TH/EN, mobile widths, both General Inquiry and Print Smart RFQ.

## Important limitations / launch gates

- No production Supabase/Resend/Turnstile accounts or credentials are bundled; live service **cannot** work before your deployment/configuration.
- Existing Quote Builder, Orders and synthetic Business Dashboard still use `localStorage`; **they are not automatically synchronized with live submissions**. Do not enter real customer data there. Live Inbox is read-only.
- Artwork files are not uploaded. Public source files are not confidential; private artwork storage and upload policies remain a later phase.
- `privacy.html` is only a draft placeholder; replace and review it before launch. Add retention/deletion, backup/restore, access audit, domain monitoring, rate limits/WAF and provider abuse controls as production policy requires.
- The staff login page is publicly loadable HTML; actual data authorization comes from Supabase Auth + DB RLS. Prevent exposing staff-only UI pages via indexing (`noindex` is not security).
- Auth login relies on Supabase email/password and requires MFA/strong password policy or SSO before a sensitive commercial deployment.
- The email outbox stores status, retries, and provider IDs; inbox delivery confirmation requires optional provider webhooks (not yet implemented).

## Why no mailto?

Opening a local mail app makes the user send again, does not guarantee delivery, may spawn multiple drafts, and does not insert the business record. In V2.5 request submission only succeeds after the server has committed the database transaction; email sending is decoupled.
